# AI 工具助手：前端壳子与 API 的通用打开方式

> **类型**：原理深挖｜**说明**：搭建属于自己的AI工具助手：前端壳子接API、配专属助手与工作模式，一条可复用的技术打开方式。

这个教程解决一件事：搭建一个属于自己的"AI 工具助手"——用前端壳子接上模型 API，配好专属助手和工作模式，让 AI 不再只是聊天的对象，而是能查资料、能跑命令、能读写本地文件的帮手。

做完你会得到：
- 一套随时可用的 AI 工作方式，
- 一条能套用到建站、部署、清理等几乎所有技术活上的通用方法论。

适用对象：会用鼠标、愿意接受命令行、想给 AI 配一个固定背景的普通用户，不需要会编程。

### 🧠 一、前置认知

##### 壳子与大脑

先说明两个概念：前端壳子与 API。

平时用 AI 聊天，其实是两层东西在协作：你看到的聊天窗口，和窗口背后真正回答问题的模型。比如大家常用的 [DeepSeek](https://www.deepseek.com/)/[豆包](https://www.doubao.com/)网页端或对应 app——网页界面、app 界面就是"窗口"，窗口下负责回复的，是服务商统一开放的模型接口。这类窗口软件叫"前端壳子"（也有人叫"前端窗口""壳工具""客户端"——叫法不重要，本质只是一个壳），负责界面、对话记录、密钥配置这些表面功夫；真正"思考"的是模型，而模型不在你的电脑上，它在服务商那边，通过 API 被调用。API 是"应用程序接口"的缩写，对使用者来说，它约等于一把钥匙加一个地址：把问题发过去，把回答收回来。

一句话：前端壳子负责"说"，API 负责"想"。

##### 自由组合

这两层可以自由组合，这是整套方法论的地基：

| 层 | 职责 | 我用的 | 同类可选 |
|---|---|---|---|
| 前端壳子 | 聊天界面、对话管理、密钥配置 | [Chatbox](https://chatboxai.app) | [Cherry Studio](https://cherry-ai.com/)、[LobeChat](https://lobehub.com/)、[Open WebUI](https://openwebui.com/) 等 |
| 模型 API | 大模型推理 | DeepSeek API | [OpenAI](https://openai.com/)、[Claude](https://claude.ai/)、[Gemini](https://gemini.google.com/)、[通义](https://tongyi.aliyun.com/)、[Kimi](https://kimi.moonshot.cn/) 等 |

我自己用的是 Chatbox，理由是足够简单：开源、免费、无广告，开箱即用，对新手友好，而且近期（2026年8月）有了工作模式后，工作能力也有了很大的提升——可以直接读写本地文件，并调用命令行了。

而 API 选用的是 DeepSeek，性价比突出（可是我的家庭条件你也知道.jpg）

理论上，你换壳或者换API都是可以的，壳子和模型互不绑定，这正是"工具助手"能长期复用的原因：哪层不好用了，只换哪层，其他可以不动。

##### 破解版的真相

理解了"壳子 + API"这套结构，再回头看网上大量宣称"破解版""破壳版""免费解锁"的 AI 软件和教程视频，底层其实都是同一个逻辑：一个前端壳子，加一个 API。区别只在于细节。

那些软件大多是把现成的开源壳子改一改、打包起来，再塞进一个来路不明的 API——可能是共享的密钥、第三方转售的渠道，甚至更成问题的来源——然后靠"大多数人不知道这个概念"赚信息差的钱：你以为买到的是高级软件，实际用的还是壳加 API，而且是被人改过的壳（可能夹带后门、广告），里面的 API 也说不准什么时候就失效——密钥被查封、渠道跑路，软件说挂就挂，更新一次就不能用了。

看清这套逻辑后，这类"破解版"的卖点就消失了：壳可以自己搭，API 可以自己买，中间那层神秘感只是信息差。反过来也一样成立——你甚至可以把自己的 API 密钥挂进"[酒馆](https://github.com/SillyTavern/SillyTavern)"这类第三方前端的壳里，拼出自己想要的使用体验；算是个延伸用法，这里就不展开了。

##### 为什么不用网页免费版

为什么放着免费的网页版不用，还要走 API 路线，付费又折腾？核心差异是三个词：可配置、可掌控、按量计费。

- 可配置：网页版只能按它给的界面用；API 路线能配专属助手、固定系统提示词、联网与代码执行的工作模式，还能把同一把密钥接进自己的脚本和自动化流水线。
- 可掌控：模型来源自己选、密钥自己管，换壳子、换模型都不影响既有配置，不绑定任何一家网页产品；哪天想换一家 API，改一下配置就行。
- 按量计费：API 按 token 计费，可以粗浅理解为按处理的字符量算钱，用多少付多少。个人日常的写作、问答、脚本调用开销通常很低，但对话越长、模型越强，花费越高；具体单价各家不同且会调整，以官方定价为准【此为推测：价格随市场波动】。

而且前端壳子不是 API 的唯一入口。同一把密钥，命令行能调、脚本能调、自动化流程也能调，聊天窗口只是最省事的入口。认识到这一点，"前端窗口 + API + 命令行"就成了一套可以自由拼接的组合拳，最后一节再展开。

一句话：网页版用的是省事，API 买的是自由度。只想偶尔聊几句，网页版够用；但一旦想让它固定背景（自定义提示词）、接进自己的工作流，API 路线才是根基。

### 🔧 二、安装部署

##### API 与密钥

模型来源我选的是 DeepSeek API。在 DeepSeek 开放平台（[platform.deepseek.com](https://platform.deepseek.com/)）注册账号、充值，创建一个 API Key（一串 sk- 开头的密钥），按量计费。密钥就是"通行证"：前端壳子拿它换取模型服务。注意保管，别贴进公开仓库或博客。不同平台的具体入口略有差异，以官方文档为准。

##### 前端壳子

下载 Chatbox（[chatboxai.app](https://chatboxai.app)），安装后选择"使用自己的 API Key"这类入口，把密钥填进去、选好模型（DeepSeek 对应 deepseek-chat 这类模型名）。不同壳子的界面不一样，但入口逻辑相同：填接口地址、填密钥、选模型。按钮名称会随版本变化，拿不准就问 AI，或看官方说明。

##### 验证连接

发一句最简单的测试消息。能收到正常回复，说明"前端壳子 → API → 模型"这条路已经通了，这是后续一切的前提。

### 🤖 三、专属助手与规则

##### 专属助手

聊天工具的默认状态是"每次都是陌生人"：新开对话就得重新交代背景。解法是系统提示词——给助手预设一段"身份说明"。做法是新建一个专属助手，把项目背景、硬件环境、目标写进系统提示词，后续对话不用再重复交代。一段示例，可按自己的情况改：

> 你是一个（项目类型）助手。项目背景：……；硬件环境：……；目标：……；工作方式：不确定的机制先查证或复现再动手，执行前说明要做什么、影响什么。

提示词写不好也没关系，把需求描述给 AI，让它帮你起草——这一步本身就是这套工作方式的第一次演练。

##### 规则文档

积累多了以后，我把不同用途的规则提炼成一份份提示词文档，统一放在 Assitant-Prompt 文件夹里，需要时用主助手调用：既能保持对话背景一致，又能按需切换规则、互不冲突。TTS 流水线的"文稿助手"、内容提炼整理助手、系统维护的决策规则，都是这么沉淀的。规则文档是"菜谱"，要自己翻出来递给厨师；这一步先做菜谱，后面有更自动化的形态（见最后一节）。

### ⚙️ 四、工作模式

其实也就是开放了常说的 Agent 能力：给它一个目标，它能自主规划、决定下一步执行什么，甚至直接通过命令行操作电脑。2025 年 Agent 的概念和应用已经集中出现（比如当年的 Manus 这类），但大多还在演示阶段，普通场景用得到的也不多；直到 2026 年初 OpenClaw（外号"龙虾"）爆火，把"让 AI 操作电脑"带到了普通人桌面上。现在看到 Chatbox 也装载了这类功能模块，就直接用了起来，体感还不错。

##### 联网搜索

工作模式第一项是联网搜索：查资料、核实官方文档和主题源码时，先搜再答，不凭记忆发挥。比如查 [Hugo]({{< relref "05.Hugo 博客从零部署到Github推送上线.md" >}}) 的配置参数、核实接口用法，有来源可循，排错才有依据。

##### 代码执行

第二项是代码执行，这是"工具助手"和"聊天机器人"的分水岭：开启后 AI 能直接在本地运行命令行、读取文件、修改脚本，再把结果交回验证。我的习惯是"先复现再动手"——拿不准的机制，先让它在沙盒里用同版本环境复现一遍，确认了再改真东西。部署 [IndexTTS]({{< relref "../05.实践日志/02.IndexTTS配音+自动字幕部署.md" >}})、写 [Whisper](https://github.com/openai/whisper) 对齐脚本，都是这样一轮轮调试出来的。这两项能力由前端壳子提供，不同壳子支持程度不同，选壳子时先确认这一点。

##### 协作分工

执行能力放开后，分工就很重要。我的原则：AI 负责执行，我负责判断。只读扫描、列清单、低风险操作交给它；涉及删除、管理员权限、软件内设置的，由我确认后手动完成。实际使用中最多的动作是 Ctrl+Shift+C——看到可疑目录，复制路径发给它："扫一下这个目录"，它回传结构、占用、可能的身份，我再决定删留。它比你更懂命令行，你只要比它更懂自己。

##### 本地模型与 RAG

早些时候（2025年底2026年上半年）还研究了下RAG，也就是外部挂载本地知识库，可以让讨论范围更集中，回复更精准。
但是需要"嵌入模型"（可以理解为帮助对话模型来精确检索文本的模型），也就是给模型用的模型。体积较小，可以通过 [Ollama](https://ollama.com/) + 命令行安装，细节可以直接问你的 AI 助手。

Ollama 这类工具可以在本机跑开源模型，把 [bge-m3](https://huggingface.co/BAAI/bge-m3) 这类嵌入模型装进 Ollama，前端就能直接调用。接本地模型的好处是数据不出本机、离线也能用；代价是吃显存。
你电脑性能足够的话，甚至可以通过 Ollama 本地装一个 DeepSeek 模型（几百G起步，还没算显存占用），然后用前端壳工具调用。

用 Ollama 装嵌入模型纯粹是出于安全性考量。云端模型当然功能会更好，但你把资料（比如论文）上传到云端模型的话，等于送给服务商白嫖，进入其数据库了。

再说回RAG，本地模型最常见的用途是给 RAG 打底。RAG（检索增强生成）的思路是：AI 回答前先"查资料"——用嵌入模型把 [Obsidian]({{< relref "06.Obsidian入门完全指南.md" >}}) 知识库里的笔记向量化，提问时检索出最相关的片段，作为上下文注入回答。

这又跟专属助手正好互补：系统提示词是固定背景，适合放不会变的项目说明；RAG 是按需检索，笔记多了以后，提示词装不下的内容，交给检索才是正解。

Obsidian（笔记库）+ 本地嵌入模型（Ollama 里的 bge-m3）+ 前端壳子的 RAG 能力，正好凑成一套"回答基于你自己的笔记"的组合拳——第二大脑的进阶用法：不只记下来，还能被 AI 按需翻出来。

现在 AI + 前端壳迭代后能直接读写本地文件，很多场景不用额外搭 RAG 也能干活；RAG 不可替代的地方在于"按需检索自己的笔记库"这件事本身。

### 🤔 五、为什么做

##### 契机：网页版的瓶颈

最初用 AI 是从网页版开始的。用得多了，撞上一个明显的瓶颈：对话一长，网页版就开始无响应——上下文被截断、请求被限流，聊到一半卡住是常事。后来查询才知道，走 API 路线能拿到更高的调用优先级、更大的自由度、更长的上下文：模型怎么选、密钥怎么配、一次能聊多长，都由自己掌控，而不是被网页版的限制卡死。这正是第一节说的"可配置、可掌控"的由来——我切到"API + 前端壳子"，直接原因就是网页版聊不长。

##### 最近发现的用法

至于让 AI 直接操作电脑——读取本地文件、执行命令行、修改脚本——是最近才发现的用法。

最初对 AI 的认知只是"给建议"：问一句，答一段。
直到 Chatbox 最近更新、开放工作模式，竟然可以直接读写文件和调用命令行了。那没的说，命令行我馋很久了，只是自己不太熟悉（流下了没技术的泪水）。这下好了，直接去掉了自己编写命令行的门槛，那直接开工。

首先就拿它来清理 C 盘做测试：AI 扫描目录、列出占用，我决定删留，它执行并回读结果验证。一台黑箱状态的电脑，就这样变成了看得见、可验证的白箱。到这一步，AI 才真正从"聊天对象"变成"工具助手"。

后续把 D 盘、E 盘也按同样的思路清理了一下（详情见：AI测试-清理维护的“[上篇]({{< relref "../05.实践日志/03.AI测试-清理维护（上篇）：C盘清理.md" >}})”和“[下篇]({{< relref "../05.实践日志/04.AI测试-清理维护（下篇）：D盘E盘大扫除&目录结构重新规划.md" >}})”）。

甚至尝试直接用 AI 帮我修订检测文章、编写和验证脚本，实测下来也都是可行的，而且效果也不错。
比如现在的博客，也都是让 AI 使用某种提炼过的统一规则重新整理润色过的。内核的内容方向、质量检测还是得自己来把控；但格式统一、细节调整这些，用 AI 显然效率和效果的表现都是相当不错的。

### 🧭 六、通用方法论

##### 组合拳

把前面的部件收拢来看，这套东西的本质是三个部件的组合：
- 前端壳子负责"说"
- API 负责"想"
- 命令行和脚本负责"做"

任意一层都可以替换——壳子能换、模型能换、执行端可以是命令行也可以是打包好的 .bat。所以凡是想"让电脑按我的想法干活"的场景，都能套这套组合。前端窗口 + API，配合命令行这些执行手段，本身就是一套通用方法论，不绑定任何具体软件。

##### 门槛与封装

技术门槛的真相往往是"默认你会"：教程默认你懂命令行、懂环境、懂英语，缺了哪一层就卡在哪一层。AI 助手恰好补上了这些断层——把"会写代码"的要求降成"会描述问题"，把"看懂报错"降成"把报错发给它"。再往深看，从命令行到 IDE 再到 AI 助手，全是一层层的封装；封装到极致，又回到了"说人话"。工具助手正是这条封装链上离人最近的一环（完整展开见《[信息技术的真正门槛：默认你会的东西]({{< relref "03.信息技术的真正门槛：默认你会的东西.md" >}})》）。

##### 沉淀与复用

最后一步，把一次性配置沉淀成可复用资产。规则文档是第一步（前面说的"菜谱"）；再进一步是打包成 skill——一组规则加脚本，由触发词自动加载执行，说一句"维护下电脑"就自动跑完体检、决策、更新、清理、验证全套流程。菜谱要自己翻出来递给厨师，skill 是装进厨房的语音厨师。一次投入、处处复用，这才是"工具助手"真正长成的地方。

##### 更多工具的底座

这套组合本身不产出成品，它是底座。前端窗口负责对话，API 负责思考，命令行负责执行——剩下能长出什么，取决于它被接到哪里：接上 Ollama 和嵌入模型，就有了第四节说的本地 RAG；接上 Obsidian，就有了可检索的第二大脑；接上 Hugo、IndexTTS 这类自部署项目，就有了从搭建到维护的全程帮手；再往上，脚本、bat、规则文档、skill 都是同一套协作框架上长出来的零件。方法论的通用性就在这里："壳 + 大脑 + 手"是一个可以自由拼接的底座，为更多复杂事项打底——想让它干什么，就把它接到对应的工具上。
