# Agent Skill 炼成与瘦身：渐进式披露原理与实操

> **类型**：原理深挖｜**说明**：给出手上 skill 从"能用"到"扛得住长期加载"的分层思路。

过去的一段时间里，我的 skill 越写越厚。规则、案例一版一版地往里加，几十行很快变成了几百行。

麻烦也跟着来了：Agent Skill 一旦被触发，正文会全量进上下文——哪怕这次只用得上其中一小节，剩下的一大堆也照样一起进来，白白吃掉 token。

这篇记录的，就是把它瘦下来的过程：先弄清加载原理，再动手改。适合已经写过、或在用 Agent Skill，却没细究过它加载机制的人；不涉及"从零写第一个 skill"。

## 🧭 第一阶段：炼成与校验

事实上，在这次优化前，我的 skill 体系已经成型，看上去没什么毛病，甚至也“运行得良好”，帮我做了非常多的事情。

可它到底有没有毛病，难说，毕竟只有我个人视角。

### 🧱 已有的那套体系

这段先简单介绍一下我自己的 skill 体系，用于经验参考和后续对照

##### 从提示词到 skill

最初是源自我常用的一些提示词；后来发现 agent 能读盘，我就把它们做成了单独的文档，供不同情景调用——感觉更方便，也能避免一开始就吃掉大量tokens

那时候还是手动：需要时翻出对应的文档、`ctrl+shift+C`拷贝路径发给对话，让它读取。

再后来，了解了“skill”这个概念后，我才反应过来：自己一直在手动做的这件事——“按需翻出规则文档递过去”，其实就已经是skill的雏形了，差的只是"自动加载"这一步。

再后来就是做成 skill，进入全自动化阶段。

因为之前详细写过，这里就不赘述了，详见 [从提示词到技能：一套自我迭代的 AI 工作流]({{< relref "../05.实践日志/06.从提示词到技能：一套自我迭代的 AI 工作流.md" >}})
。

##### git 与迭代器

而且在着手提炼 skill 的初期，我就意识到：skill 这东西，应该是类似软件，能**统一管理**；甚至由于 agent 的特性，它也应该能**自我迭代**。

于是先照这个思路，设定并练成了一个"管理所有 skill 的 skill"——迭代器 skill-evolver。

它内嵌了一套迭代协议：收集反馈、归类起草、等我确认、版本化备份、骨架同步检查、归档验证结论。底线只有一条——规则的改动必须经我确认，AI 只负责收集和提议。

配套的是版本回溯双通道。git 仓库负责可 diff、可回滚，顺带也能当备份用（可参考 [Obsidian 库 GitHub 备份完全指南]({{< relref "07.Obsidian 库 GitHub 备份完全指南.md" >}})）；各 skill 目录下的 `backups/` 快照，负责"看得懂的历史"。一个管精确，一个管可读，互不替代。

##### 自成体系的套组

然后每个skill的功能、目标虽然不同，但也都设置了相同的结构：
- 一套"本体 + 日志 + 备份 + 脚本库"的组合

外头再套一层 git 备份和统一的迭代器。

四样东西各司其职：
- `SKILL.md` 是本体
- `CHANGELOG.md` 记变更
- `backups/` 存旧版
- `scripts/` 放可执行脚本。

单看这套配置，我个人认为，这已经比多数人能想到的更完整了。

### 🪞 反思与寻求校验

但是，，虽然体系看着齐全了，但隐约感觉还是有点缺失。

因为这些 skill 基本是直接让 agent 自己练成的，等于信息源只在 AI 本身。

虽然通用知识出错的可能性不大，过程中我也按经验修正过。可渠道毕竟单一，于是就想往外找一份对照，拿外来的说法再校验一遍。

##### 外部探索

于是我先去 B 站搜了一圈，找到一篇综合数据评价不错的视频——《Agent Skill 从使用到原理，一次讲清》。

17 分钟，播放 94 万，收藏率 5.46%，是我看过的同类工具讲解里最高的一档。

顺手把它交给了自己练成的内容抓取 skill（bili-note），让它抓字幕、做整理，正好当一次实战。

##### 内容概览

视频讲的，是 Agent Skill 的定位与本质（一句话——"大模型可以随时翻阅的说明文档"）、核心加载机制"渐进式披露"，以及它和 MCP 的分工。

##### 互相印证

我参考其中讲解的原理，一条条对照自己已有的 skill 体系，发现：

- 我已经做到的：规则的固化和自动调用
	- 把规则写成 `SKILL.md`、靠触发条件自动加载。
- 视频没提、但我已经做了的，这部分走得比视频更前：
	- 自我迭代与统一管理（skill-evolver 加迭代协议）
	- 按个人需求定的设计（隐私边界、触发后改变流程等）
- 该做、可以做，但我还没做的
	- 视频点出的"上下文成本"这一层。

我原本的关注点全在"工程管理"——版本、备份、日志；却没有一条机制，去管"这个 skill 每次触发到底吃掉多少上下文"。

看来问题就出在这个地方。

## 🔍 第二阶段：原理详解

视频里管这个叫"渐进式披露"，简而言之：内容按需一层层揭开，不必一次给全。

### 🧩 SKILL 的三层结构

这三层从外到里，加载门槛一层比一层高。

##### 元数据层

每个 skill 的 name 和 description。它们始终对模型可见，说白了就是一份目录——模型每次回答前先扫这一层，判断这次的问题该归哪个 skill。代价极小。

##### 指令层

`SKILL.md` 里除 name、description 之外的正文。它只在 skill 被命中时才加载；但一加载，就是整份全量进上下文，没有"只读某一节"这种好事。

##### 资源层

`references/` 和 `scripts/`（官方规范里还有个 assets）这类附属文件。它是"按需中的按需"——只有指令层判断出需要，它才会被读进来。

### ⚙️ reference 与 script

资源层里这两样东西，机制完全不同。这是全篇最该记住的一点。

##### 读，还是跑

reference 是"被读取"的——内容进上下文，供回答参考；script 是"被执行"的——模型压根不看代码内容，只关心怎么调用、跑出什么结果。

##### 成本两极分化

一个读、一个跑，成本就两极分化了：reference 会消耗 token，script 几乎为零。

视频里那句说得很到位——"哪怕脚本写了一万行，消耗的上下文也几乎是零"。

但有个前提：要是 `SKILL.md` 里没把"怎么运行"交代清楚，模型跑不下去，就会转头去翻代码。这一翻，照样开始吃上下文。

所以脚本的调用方式，必须在指令层写明。

## 🛠️ 第三阶段：查漏补缺与回炉

原理弄清，动作就明确了：先拿它当尺子把库扫一遍，定下标准，再动手搬。

### 🩺 状态自查

##### 实用性良好

拿三层结构逐格对照已有的实现，结果还不错：description 写了触发与不触发条件，正文有意压薄，resources 和独立知识库目录都在用，脚本走的也是"执行"这条路。

功能上基本符合——说明这套体系本身没走偏。

##### 体积膨胀

可一量体积，问题就露头了。

最重的三个：skill-evolver 44,547 字、xiaoxiao-xiuxian 53,980 字、personal-strategy 17,093 字。

原因也清楚——日志堆在正文里、正文塞着一堆只在特定情况下才用的可选规则；还有一种更尴尬的：规则明明立对了，自己却没遵守。

（尤其难看的是，这几个里还有一个，专门管着别的 skill。）

### 📏 标准制定

得先立把尺子，不然没章法。

##### skill 字数限制

阈值不能拍脑袋，得从数据里长出来。

把全部 skill 量一遍：中位数约 7,854 字，说明"够用"的 skill 自然重量就在 8,000 上下；真正的断层出现在 17,000 到 44,000 之间。

于是定成软线 10,000、硬线 15,000。

后来还补了一层——按类型分档：回答"怎么判断"的判据底座型（比如 personal-strategy）天然更重，取软 15,000 / 硬 20,000；回答"怎么操作"的流程执行型，取软 8,000 / 硬 12,000。

##### 专属知识库设计

搬出去的东西要有落点，否则就是白搬。

约定很简单：一条 skill 对应一个专属知识库，互相隔离——既存相关文档，也放运行缓存，彼此不串。

碰到内容提炼、文案拟定这类跨 skill 共用的核心规则，就单独放进一个共享库，省得各存一份、必然漂移。

##### 内容拆分规则

一块内容到底留正文还是搬走，就看三条判据：

- 在场判据
	- 看它"要不要在推导那一刻在场"。
		- 有些历史虽旧，功能就是防止重新推导（比如已作废的结论），那就必须留在正文；
		- 来源日期、推导过程、案例细节这类不需要在场的，才回流到资源层。
- 分支判据
	- 只在特定条件下才会用到的，外置即可
	- 正文里只留"什么时候走这个分支"。
- 类型判据
	- 按 skill 类型分流，判据底座型多留，流程执行型多搬。

##### 命名与索引

外置文件要有统一的命名规则，每个知识库再配一份索引，写明"哪个场景读哪个文件"，回查时才好定位。

### ♻️ 回炉重构

标准定完，就是动手搬。

##### 留条件指针

每搬走一块，正文原地得留一行条件映射，像"清背包读 `03.物品-药材.md`、炼金读 `04.物品-丹药.md`"这样。

没这行，搬走就等于失联。

##### 外置与去重

搬的时候，顺手做一次去重。

实际扫下来发现，有些内容根本不用搬——知识库里早就有同一份，正文那段纯属双份漂移，删掉就行。

##### 记账与备份

每改一步，改前把旧版复制进 `backups/`，改后在 CHANGELOG 记一笔：改了什么、为什么。

### ✅ 验收复盘

##### 校验脚本

光靠自觉不够，得有个闸门。

于是在原有的 skill 校验脚本（`validate-skills.mjs`）里，加了几条"结构卫生"检查：`SKILL.md` 字数（超硬线报错、超软线警告）、正文里混没混进 CHANGELOG 段（必须外置）、有没有版本版头、元数据是否合规。

这样每次迭代跑一遍，问题自己就报出来了。

##### 复扫修正

闸门自己也会出错。

它最初用精确匹配查版头，把"`## 当前版本：vX`"这种行内带版本号的写法误报成缺失，改成前缀匹配才正常。

二次复扫还推翻了一个判断：上一轮因为没去查外部知识库有没有对应文件，误以为某个 skill"搬不动"，据此新设的档位后来被撤回。

说白了，判"能不能搬"之前，先查外部库，是硬前提。

## 📌 总结

### 📊 效果展示

##### Skill 瘦身完成

一轮下来，几个主要 skill 的体积变化：

| skill | 瘦身前 | 瘦身后 | 变化 |
|---|---|---|---|
| xiaoxiao-xiuxian | 53,980 | 11,707 | -78% |
| skill-evolver | 44,547 | 7,247 | -84% |
| personal-strategy | 17,093 | 14,710 | -14% |

顺手把字数闸门、日志外置、版头、元数据四类检查，固化进了校验脚本。

（说句实话，看着这几个数掉下来，还是挺解气的。）

##### 规则进一步完善

瘦身过程中，沉淀了几条可复用的判据（在场、分支、类型），还有一条元规则：规则的执行者，必须与规则制定者分离。

三个出问题的 skill 有个共同点——规矩写得很对，自己却没守。

那条元规则说的就是这件事：光写对不够，得有机制逼它遵守。校验脚本扮演的，正是这个执行者。

### 💭 延伸思考

##### 交叉验证

这次往外找对照，其实是一次"不盲信单一信源"的实践。信息源哪怕是自己信任的 AI，也值得再过一道外部校验。

至于一条外部信息该不该采信、信到什么程度，可以参看[AI时代的信息判断原则：认知局限与真假判断]( {{< relref "09.AI 时代的信息判断原则：认知局限与真假判断.md" >}} )里的思路。

##### 迭代机制的重要性

能让这套东西长期跑下去的，是迭代机制本身：版本化让改动可回溯，执行者与制定者分离让规则真的被执行。

内容会过时，机制不会。这也是为什么——什么都可以改换，迭代器最好还是要有。
