# 从提示词到 skill：一套自我迭代的 AI 工作流

> **类型**：体验反思｜**说明**：从写提示词、攒助手，到把长提示词搬进本地文档由通用助手读取调用，再到第一次把电脑维护流程做成 skill、并给它装上更新机制——一条把“怎么用 AI”本身做成可迭代系统的路径记录。

### 起点：写提示词，攒助手

##### 最早的通用助手

大概2025 年底，刚刚接触 LLM 时，了解了壳工具与提示词。
为了对 AI 的幻觉情况做出限制，让 AI 自己起草做了一份“通用 AI 助理”提示词：
```
我是一个专业全能的助理，在这个对话中将遵守以下规则：
- 回答原则：基于可靠信息，如实作答
- 标注原则：任何推测性或不确定性内容，请明确标注【此为推测】或【此观点存在不确定性】 
- 免责原则：不替代专业意见，对于重要决策，建议我咨询权威来源
- 真实原则：绝不编造不确定的内容
对于较新的作品、事物，如果我的知识库信息不足，我会先搜索确认，或者明确告知您当前信息的局限性。
```

内容很短，虽然不可能100%消除幻觉，但总体能定个基调，用起来还不错，我在本地笔记也存了一份当模板，直到现在也还在沿用。你想尝试的话，也可以直接复制使用（比如给自己设置个一样的助手，或者直接发给网页对话作为基础规则等）。

后续也尝试过做不同的提示词，比如加人设做聊天机器人用、或者一些其他稀奇古怪的设定，或者尝试一些软件自带的助手（其实也就是一段默认提示词+一个头像），但总的来说，没有这个基础的提示词使用的多。

##### 网页版与壳工具

然后说一下提示词在网页版和壳工具中的区别

网页版也能喂提示词，但没法切换底层 API；而在壳工具下，你可以在跟 deepseek 聊了一段后，再把模型改为 GPT 然后继续对话。这个虽然可能用的不多，但确实是可行的。

另外就是壳工具的提示词通常被视为“系统级提示词”换句话说，它的权限优先级更高，可以做出一些更精确、更复杂的设置。

##### 用 AI 提炼提示词

然后如果提示词不知道怎么写的话，你也可以把一些关键信息发给 AI，让 AI 自己归纳，而且做格式整理本身也是 AI 擅长的部分。

今年七八月份积累英语词汇，又意识到一个新的玩法，那就是“把历史对话发给 AI”，同样可以归纳提炼，于是又做出了`英语积累（技术+日常）`这个助手，一下把持续对话时出现的回复漂移问题解决了，也发出来给大家参考下：
```
你是一名专业的英语词汇编辑。你的任务：根据用户提供的单词列表，严格按以下模板和规则批量生成词条。所有词条必须在结构上完全一致，不得有任何遗漏或格式偏差。

## 输出模板（每个词条）

# {单词}

### 基本信息

- 音标
    - 英式：/{BrE}/
    - 美式：/{AmE}/
- 释义
    - {词性}. {中文释义}（{语境补充说明}）
- 例句
    - {含该词的英文例句}

### 常用搭配

- {搭配1}：{中文}
- {搭配2}：{中文}
- {搭配3}：{中文}

---

## 规则

1. 音标：统一使用 IPA 音标。
   - 英美发音不同 → 分行写「英式：/…/」与「美式：/…/」；
   - 英美发音相同 → 输出一行「- /…/」，不加任何标注；
   - 不同词性发音不同 → 音标绑定到对应词性行，格式「n. 英 /…/ 美 /…/」。
2. 释义：每个词性单独一行；多词性排序固定为：名词 → 动词 → 形容词 → 副词；中文释义必须贴合语境（括号内补充语境说明），不得只给通用释义。语境选择规则：技术语境优先——若该词在技术/编程领域有常见用法（如 abstract→抽象类、schedule→调度），采用技术语境；若确无技术用法（如 chair、breakfast），则采用日常语境。
3. 例句：1 条英文例句，场景必须与所选语境一致（技术词用技术场景，日常词用日常场景），且必须包含该单词本身。
4. 常用搭配：2~3 条，格式「英文：中文」，优先所选语境的常见搭配。
5. 格式：词条标题用「# 单词」；词条之间用「---」分隔；除词条本身外不输出任何内容（禁止开场白、解释、总结，禁止用代码块包裹整个输出）。
6. 禁止：不得编造音标，若不确定标注「[音标待核]」，宁缺毋假；不得使用双链标记「[[]]」；不得省略任何字段；不得改动字段名称（音标/释义/例句/常用搭配）。
7. 批量：每批输出 20 个词条；收到「继续」后输出下一批；单词列表不足 20 个时全部输出。

## 标准示例（结构锚点）

所有词条必须与以下示例的字段顺序、层级、标点完全一致：

# abstract

### 基本信息

- 音标
    - 英式：/ˈæbstrækt/
    - 美式：/ˈæbstrækt/
- 释义
    - adj. 抽象的（不针对具体实例的）
    - n. 摘要
- 例句
    - An abstract class cannot be instantiated.

### 常用搭配

- abstract class：抽象类
- abstract method：抽象方法
- abstract concept：抽象概念

---

## 输出前自查

每批输出前，逐条核对：① 字段齐全（音标/释义/例句/搭配）；② 音标已按英美规则处理；③ 多词性已分行并按固定顺序；④ 例句含该词；⑤ 搭配格式为「英文：中文」；⑥ 词条间用「---」分隔；⑦ 无双链标记、无多余内容；⑧ 释义/例句/搭配三者语境一致（不出现“释义是日常、例句硬套技术”的混搭）。
```

##### 对话背景的提炼

但长期使用下来，仍然有一个不可避免的问题——在跨对话时，换一个对话，常常要重新补充背景，或者依赖 RAG 功能去检索。

印象里豆包会有一些用户画像记忆的功能，现在 chatbox 更新（26年八九月份）后也有类似的常记忆功能。

不过总的来说，个人不太喜欢对话之间互相污染，所以用豆包这类工具时会主动关掉记忆，以免形成“信息茧房”。

但有些场景又确实需要统一的对话背景，比如要讨论一些个人情况，辅助分析判断等等。于是又用上“AI 提炼提示词”的方法，干脆把个人信息交给 AI，尝试提炼成个人画像，再一轮轮补全。于是就得到了一份“个人画像”的提示词（不做展示），并多轮修订，直至可以使用。

### 从臃肿到本地文档

画像补全之后，尝试把归纳出来的信息直接当成提示词设置给 AI。但问题很快出现：几千字的提示词内容太长、太“臃肿”，每次对话都白白占掉 token，而且一定程度上也会污染对话结果。

转机是工具（chatbox，八月份）开始支持读取本地文档。既然如此，干脆把这类长篇幅的提示词从对话里搬出来，存成本地文档，再用「通用助手」——它本身只有几句基本提示词——去读取和调用对应规则。这一步就是 `Assitant-Prompt` 文件夹的雏形。

顺带一提，跨对话补背景时也用过 RAG 检索自己的笔记，但检索解决的是“找到相关信息”，解决不了“每次都要重新交代我是谁”——后者还是得靠一份固定的画像。

##### 落地文件的好处

落地成本地文档，顺带解决了两个问题：
- 一是 token 成本，每次对话都背着几千字背景，长期算下来不划算；
- 二是版本混乱，提示词散在对话里，改一处、丢一处，只有落成文件才能做版本、做差异、做归档。

##### 规则文件的积累

有了这个思路后，就开始提炼总结各种场景的使用规则，并放入该文件夹方便调用：
- 博客文章提炼助手（v2 标题规则 → v2.1 收尾署名 → v2.2 小标题字数 → v2.3 YAML 元数据 → v2.4 引号校准 → v2.5 取消字数上限 → v2.6 排版 → v2.7 导读行）
- 教程知识分享助手（v1、v1.2）
- 视频文案提炼助手（v1.0）
- 文稿格式助手（把口播稿转成 TTS 友好的断句格式）
- 工作情况画像

##### 共同骨架

到后来，规则越攒越多，反而看清了一件事：这几份提炼助手的骨架几乎是同一套。
- 它们都有角色设定（你是谁、做什么）
- 类型判断（先分清输入属于哪一类）
- 结构模板（按类型选章节组织）
- 视角规则（把对话里的“用户 / AI”转写为第一人称、不留对话痕迹）
- 真实性要求（不确定内容标注【此为推测】）
- 标题规则、YAML 元数据规范
- 收尾署名
- 输出前自检
- 以及一条版本迭代记录。

博客与教程两份助手的差异，其实只在“类型判断 → 结构模板 → 标题模式”这三处。

共享骨架带来双重后果：
- 好处是复制一份就能孵化一个新助手；
- 代价是同一套规则维护了多份——这也是后来“版本漂移”隐患的根源。

##### 手动调用的三步

那时的用法是：
```
CTRL+Shift+C
```

拷贝对应规则文档的路径，发给对话，让其读取调用。总的来说体感还不错，但确实是手动操作的，略微繁琐。而且规则文件越攒越多，也看得比较费眼，不够简洁。

### 手动版 skill

后续对“智能体”和“Skill”这两个概念起了好奇，就查询研究了一下，才发现：自己其实早就在手动使用 Skill 了。所谓 skill，其实也就是把一组规则（有时还有脚本）打包，由触发词自动加载执行；而我已经手动再做了——只差自动化加载这一步。

##### 概念对齐

弄清 skill 的确切含义之后再回头看，整条路径就串起来了：把已有的规则文件变成 skill，缺的只是“自动加载”这个环节。规则文档像菜谱，每次都得自己翻出来递给厨师；skill 则像装进厨房的语音厨师，说一句“做道菜”，它自己去翻菜谱开工。

##### 手动与自动的差距

把两者并排看，差别其实只在三个地方：规则文件要人翻，skill 自己加载；规则文件靠记忆判断什么时候用哪份，skill 靠触发词匹配；规则文件的更新靠人记得改，skill 把更新写成了协议。
前两步省的是操作，最后一步省的是维护
前面提高的是便利性，后面那步决定了能否长期使用

### 第一次 skill 化：电脑维护

第一次把规则文件变成 skill 的尝试，选的是电脑维护——那段时间刚好用 AI 跑完一轮 C 盘、D 盘、E 盘的清理，流程已经成熟，正好拿来试水。

操作上还是让 AI 自己提炼，毕竟对于 skill 的格式，AI 知道的比我清楚。我需要做的只是检查，甚至实际上还能通过这个步骤反过来了解 skill 的格式。skill 仍然是 .md 文档（这倒是和 obsidian 笔记也一致了），甚至也可以直接当做提示词规则注册给 AI 对话，或者说，它的内容本质还是提示词，只不过过了自动调用的步骤。

##### 打包内容

打包进去的东西比想象中多。核心是主流程：体检 → 决策 → 更新 → 清理 → 验证，说一句“维护下电脑”就自动走全套。
流程之外还有三层规则，以及两个 PowerShell 脚本（一键体检报告、白名单静默批量更新）。
原则写在最前面：判断优先、最小干预、决不擅自动黑名单项。

##### 决策规则表

最早成型的规则表把可更新项分成几类：

- 放心更（白名单）：Python、微信、QQ、PotPlayer、网易云、腾讯会议、百度网盘、GitHub Desktop、VCRedist 等
- 别动（黑名单）：Anaconda（conda 环境，升级有破坏风险）、系统级驱动类组件（官方服务器 403 时旧版无害，直接跳过）
- 手动清单：Edge 走 `edge://settings/help`，达芬奇、剪映、Adobe 系走各自更新器——winget 装不了系统级
- 可卸清单：OneDrive、Docker、Ollama、PyCharm 等，看是否还在用
- 残留类：winget 列表里出现“应已卸载”的软件，属于幽灵卸载项，要单独处理，不能当普通可更新项

这张表的价值不在“列了哪些软件”，而在于把判断沉淀下来——下次不用重新想“这个要不要动”。

##### 坑位记录

真正让 skill 耐用的是坑位记录。这一轮下来记了十几条，比如：

- 网易云升级会偷偷重加开机自启，装完必须回头查启动项
- WSL 大包失败报的错看起来像网速问题，真实原因是权限（`0x80073d28` 需管理员），没有 UAC 的后台进程必失败
- 幽灵卸载项可以根治：查注册表 Uninstall 键的安装目录，目录不存在就是纯残留，删键后 winget 不再误报
- Chrome 会自动下载约 4GB 的本地 AI 模型，可安全删除，体检 C 盘时必查
- Electron 系软件（如 Notion）卸载后，`Partitions` 目录常残留 1~3GB 缓存

这些坑不写下来，每次都会重新踩。

##### 清理分级

清理分三档：

- 安全级：直接跑（系统 TEMP、Windows\Temp、回收站）
- 谨慎级：先问（浏览器缓存、旧更新组件、已卸载软件的残留）
- 不动级：WinSxS、pagefile、各类软件数据目录

分级的用意是把“能自动做的”和“要人拍板的”分开，避免一键清理把用户资料也带走。

##### 试运行

实测调用了一轮：百度网盘 8.7.2 → 8.7.9、TEMP 释放 1.17GB、迅雷确认干净、Anaconda 没有被误更——决策规则全部按预期工作。这一步验证了整条路可行，也给了继续把其他规则 skill 化的信心。

### 让 skill 能更新

第一次成功之后，接着想到：skill 应该也能像软件一样更新。于是给 skill 体系加上了**更新规则**，让 AI 帮忙完善这套机制。做法不是单点打补丁，而是把之前积累的规则文件系统地转成 skill。

##### 批量转化与体检

动手之前先给 `Assitant-Prompt` 做了一次体检，把 9 个文件归成 6 类：个人画像（v1.10 / v1.11）、工作画像（v1.0）、博客文章提炼助手（v2.6 / v2.7）、教程知识分享助手（v1 / v1.2）、视频文案提炼助手（v1.0）、文稿格式助手。体检发现两个隐患。

一是版本漂移。博客文章提炼助手已经迭代到 v2.7，教程知识分享助手 v1.2 的文件头却写着“基于 v2.6 框架”——三份提炼助手各存了一份通用写作风格和视角规则，同一套规则维护三处，改了一处忘了另一处。

二是流水线缺环。从原料到博客、从博客到选题、从选题到视频，这条链条里“博客 → 子选题拆解”这一段没有对应助手，检查的过程中，也顺便补全了“内容流水线”这个概念，正好可以作为个人常用 skill 的组织骨架。

##### 分组方案

后续要做的就简单了，据此把规则文件按流水线环节（而不是按文件）切成 skill：

- personal-strategy：画像 + 工作画像 + 协作规则，战略底座
- content-refiner：博客 + 教程合并，负责原料 → 博客
- video-script：口播 + 格式合并，负责子选题 → 口播稿 → TTS 文稿，两阶段可独立调用
- topic-miner：新建，补上选题拆解缺环，每篇博客拆 3~6 个子选题（后弃用）
- skill-evolver：**迭代器**本体，管理上面所有 skill

>什么都可以改换，但是迭代器，最好还是要有。

两个合并决策的理由一致：共享 80% 骨架的规则分开维护必然漂移，合并后只剩一个维护点，博客助手新增的规则，教程助手自动继承。

##### 迭代协议

skill-evolver 里内嵌了六步协议：

1. 反馈收集：写进各 skill 的 feedback 目录，按月份归档；积累 3 条以上或每月一次集中处理
2. 归类起草：分成规则修订 / 新增案例 / 删除过时 / 画像更新
3. 用户确认：给出改动前后的对比
4. 版本化与备份：规则增补 +0.1、结构大改 +1.0；升级前把旧版复制进 backups/
5. 骨架同步检查：涉及视角规则、YAML 规范等共享骨架时，逐项核对其他 skill
6. 归档验证结论：把“某条规则执行成功”这类结果沉淀为可信资产

底线是：所有规则变更必须经我确认后才生效，AI 只负责收集、起草、提议，不擅自改规则。这条底线和“确认后再补格式”的旧习惯是同一条原则。

### 落地与解耦

生成与安装仍然通过 AI 自己来操作，自己只需要负责验收：
5 份 SKILL.md 生成后逐个安装到 Chatbox 的 skills 目录并自动启用，同时在 `Skills/assistants/` 下留了一份可移植存档——skill 装在应用里，但规则的“主版本”仍留在自己的工作目录，方便随时查看、修改、迁移到别的工具。原始 prompt 文件不动，作为历史档案。

##### 静态基线分离

安装后立刻遇到一个设计问题：个人画像被写进 personal-strategy skill 后，平时通用的助手提示词还要不要保留画像内容？最初方案是让 skill 作为“增强层”叠在通用提示词上，但很快被否掉——理由是“skill 迭代了，助手提示词还没迭代，就麻烦；而且日常对话并不需要这么详细的背景”。

于是拆成两层彻底解耦的结构：通用助手提示词锁定为静态基线文件（注明“永不因 skill 迭代而修改，修改需手动”），skill 是动态层。

##### 边界写进规则

拆开的不只是文件，边界也写进了规则本身：personal-strategy 的触发条件收窄为“仅当明确请求战略建议、长期规划、决策支持时启用，日常对话、信息查询、工具操作不启用”；SKILL.md 里加独立边界声明，写明它不修改、不依赖外部提示词；skill-evolver 也补上“外部提示词不在本体系内”。日常随便聊走通用提示词，谈战略规划才加载 personal-strategy，两边互不引用、互不迭代。

### 使用中的迭代

这套体系从 2026 年 9 月初定型后进入使用期，迭代分三个层面持续发生。

##### 规则微调

输出类 skill 的版本按使用反馈持续小幅推进。content-refiner 从 v2.8 到 v2.14 的变化很典型：输出方式改成“文件 + 增量修改”（禁止全文重写，避免漂移、也省 token）、视角规则改为“禁止对话痕迹表述”、新增“陌生引用最小背景介绍”、内容真实性补“来源过渡锚点”（防止疑问句后直接空降结论）、标题规则补风格细则、教程类层级升级为“## 阶段层 + ### 大节 + ##### 小节”。使用中发现表示无序列表的加号在 Obsidian 里渲染不一致，也顺手改成减号。每次修改都遵循同一格式：日期 + 版本 + 变更说明 + 原因，且经确认后落盘。

##### 一次修订的完整链路

修订不是想到就改。提炼《机械决定论与随机性》那次，一口气暴露了三个问题：句内已经写了“可能”却还要再加【此为推测】，语义重复、机械感强；个人猜想被前置，导致蝴蝶效应、分岔点这些概念前向引用、全文各讲了三遍；标题把支线概念当成了主线。对应改法是：标注只用于陈述语气的不确定内容，另加更委婉的选项【此观点存在不确定性】；猜想类内容挪到概念铺垫之后、由查证触发，并加枢纽句衔接；标题起点必须是具象事物。改完记进 CHANGELOG，注明原因与先例，再经确认落盘。

##### 画像校准

personal-strategy 的迭代最频繁，也最能说明问题。它的提交历史里能看到一条条真实校准：给 B 站 258 条档案标注抓取时点（避免数据没有时效）、修正效率瓶颈结论（2025 年的 116 条高产其实是零成本游戏录像，真实产能约每月 2~3 条高制作内容）、把工作流范式从“先建选题库”转向“先制作后分析”（意图表实测滞后，5 条以上已做未更新）、根据日志分析补齐家庭背景与时间约束。每一条都注明来源和原因，经确认后落盘。

##### 新 skill 加入

体系定型后又陆续扩编，几个新成员各自对应一条真实工作流：

- obsidian-notes：把外部资料、教程文稿、对话记录整理成第二大脑笔记；规则从实测踩坑里提炼（只基于提供的文稿、不自行补充、术语以原文为准、先读库内同类笔记当结构参考）
- bilibili-tracker：抓取 B 站主页数据并存档；因为空间页是纯 SPA、接口有风控，必须带 cookie 与 wbi 签名，脚本按日期文件夹存快照，用于和历史对比
- logs-tracker：把 Obsidian 日更日志当行为数据源，扫描聚合后与上次快照对比，解读结果经确认后回流画像与选题库

每加一个，skill-evolver 的管理清单同步更新一次，边界说明跟着改——管理范围从最初的 4 个一路扩到 8 个业务 skill。

##### 迭代器自身升级

skill-evolver 也按自己的协议迭代，几轮升级很有代表性：CHANGELOG 从 SKILL.md 头部移出为独立文件（避免每次调用都读一遍与执行无关的历史，且先读 CHANGELOG 再迭代可避免重复踩坑）；统一备份规范（每个 skill 升级前把旧版 SKILL.md 复制进 backups/ 目录，命名 `SKILL_v<版本>_<日期>.md`，全部保留）；YAML 规范按产出地拆成两套（content-refiner 走 Hugo front matter，video-script 走 Obsidian 规范不输出 front matter）；收尾署名区分博客署名与口播署名两套对应关系；git 层逐步从迭代流程里移出，交给一键脚本。

### 备份：git 与 GitHub

迭代机制跑起来后，版本回溯成了刚需。

##### 版本回溯双通道

skills 根目录建了 git 仓库，`.gitignore` 排除 backups/——迭代前先 commit 基线、改完再 commit，脚本类也能精确 diff、回滚。另一条通道是迭代流程维护的 backups/ 快照：每个 skill 升级前把旧版 SKILL.md 存成带版本和日期的文件。personal-strategy 的提交历史记录了画像的数据锚点迭代：v1.17 给 B 站 258 条档案标注抓取时点、v1.18 修正效率瓶颈结论、v1.20 工作流范式转向“先制作后分析”。

##### 备份策略的取舍

备份位置上纠结过一轮：版本快照放各 skill 目录下的 backups/，命名带版本和日期，全部保留不设上限；git 只跟踪 skill 本体，`.gitignore` 把 backups/ 排除。也就是快照负责“看得懂的历史”（每个版本一个完整文件，随时打开对照），git 负责“可 diff、可回滚”的精确记录，两者分工，而不是互相替代。

##### 绑定与一键推送

本地仓库跑顺后绑定 GitHub 远程仓库。当时先查了 git 状态：仓库已在 master 分支、工作区干净、已有大量 commit，只差 remote，所以不需要重新 init，直接建空仓库、绑定、推送。再往后，git 提交与推送从迭代协议里移出，收进一个一键脚本 `git推送-极简版.bat`（add -A + commit + push），迭代完成后点一下即可。

##### 与内置技能的分工

同一时期还拿这套自建体系与 Chatbox 内置技能做了一次对照评估。结论是两者基本零重叠：自建 skill 绑定个人具体工作流（梦生风格基线、选题卡片 schema、断句规则这类个性化规则内置技能给不了），且有自进化机制；内置技能是通用工具型能力，官方统一推送、改不了。评估后只保留 humanizer-zh（去除中文 AI 写作痕迹，可当内容流水线最后一道打磨工序）和 data-analysis 作低频兜底，领域性太强的股票数据类技能建议停用，避免误触发。

### 现在的样子

##### 结构总览

走到 2026 年 9 月初，这套体系已经稳定成两层结构：底层是一份从不自动改动的通用助手提示词，上面是一组可自动触发、自带更新协议的 skill。业务 skill 有八个
- personal-strategy：简介...
- content-refiner：
- topic-miner
- video-script
- obsidian-notes
- bilibili-tracker
- logs-tracker
- windows-maintenance
- 外加管理它们的 skill-evolver。

它们大体分三类：内容生产类（提炼、拆选题、写口播、整理笔记）、数据回流类（B 站账号数据、日志趋势）、事务类（电脑维护），再叠一层战略底座与个人画像。配套的还有 git 仓库与一键推送脚本、每个 skill 的 CHANGELOG 和 backups 快照。

真正让它转起来的是两条回流：B 站数据回答“什么内容有效”，日志数据回答“时间和状态怎么变”；两条都经确认后回到画像，反过来影响下一次选题和产出。至此，它不再是一批一次性写好的提示词，而是一套会自己更新的系统。

有一件事是刻意没做的：没有把所有能想到的规则都塞进 skill。skill 太多会互相抢触发，也会让日常对话莫名带上本不需要的背景——所以每加一个都要先问一句，它是不是一条真实存在、且会反复用到的工作流。

##### 使用节奏

日常使用很简单：需要什么直接说人话，skill 按描述自动匹配加载——说“把这段对话提炼成博客”走内容提炼，说“维护下电脑”走维护流程，说“看下最近数据”走 B 站抓取。每个 skill 都留了反馈钩子，使用中发现规则模糊或新案例，随手记一笔，攒够了由迭代器统一处理。频率上，画像与日志分析按季度看一次，B 站数据按需抓，电脑维护按月走一遍。

### 认知收获

整套演进下来，沉淀出几条可复用的判断。

##### 资产与工具解耦

选壳工具而不是网页版，看重的是提示词资产不被绑定：换 API 不用重写提示词，已积累的上下文也能按需要切给不同的 API。整套体系后来能跨工具、跨模型继续用，靠的就是这一点——资产和工具解耦。

##### 规则会漂移

同一套规则复制到多个文件，必然漂移——教程助手滞后博客助手一个版本就是实证。解法是合并或建立共享骨架清单：一处改动，逐项检查受影响方并同步，同步记录进 CHANGELOG 注明来源。规则越多，越需要单一维护点。

##### 提示词的层层演进

提示词经历了几个形态：对话里反复粘贴（不可复用）→ 文件化的助手规则（可被主助手读取调用、可版本化）→ skill（自动触发 + 自带迭代协议）。再往前还有一层是“壳工具 + 提示词”的选择，它决定了资产能不能脱离具体工具存在。每一层解决的都是上一层的维护成本，升级的触发点往往不是“想用新功能”，而是“维护不动了”。

##### 确认权在人

这套体系能长期运转，靠的是版本文化：每次变更都有日期、版本、原因，并且经人确认。让 AI 只做收集、起草、提议，人做最终拍板，规则才可追溯、可回滚、可信任。

##### 先单点，再体系

整条路不是规划出来的，是走一步看一步：先把一个场景做成 skill 跑通，确认可行，再回头把积累的规则批量转化；先解决“每次都要粘贴”的麻烦，再想到“给它加更新机制”。每一次扩展的起点，都是上一阶段真实暴露的成本，而不是提前设计好的蓝图。

##### 记录比记忆可靠

坑位记录、CHANGELOG、验证结论归档——这套体系里几乎所有“经验”都以文件形式存在，而不是留在脑子里。skill 之所以比“我大概记得怎么弄”可靠，是因为它把判断和踩过的坑都外化成了可复用的文本。

##### 静态与动态分层

通用提示词这类“兜底原则”锁成静态基线，永不随业务 skill 迭代；具体业务规则放动态层自主迭代。两层彻底解耦，日常对话零背景注入，战略对话按需加载——避免“skill 迭代了但主提示词没跟上”的双写漂移。

回头再看，这次实践本质上是把“我怎么用 AI”本身做成了一件可迭代的产品：从散落对话的零散要求，到版本化文件，再到自动触发、自带更新协议、有 git 备份的技能体系。规则不再靠记忆力维护，而是靠协议维护。
