# AI测试-清理维护（下篇）：D盘E盘大扫除&目录结构重新规划

> **类型**：体验反思
> **说明**：AI 能力测试系列的下篇——让 AI 跑命令行，自己只做判断，完成 D 盘、E 盘大扫除和目录结构重新规划，累计找回四百多GB空间。

> 含灵视内容：看完后，你对"卸载软件"和"电脑管家"的看法可能回不到从前。

## 🧹 从卸载网盘开始

上篇记录的是 C 盘清理（[AI测试-清理维护（上篇）：C盘清理]({{< relref "03.AI测试-清理维护（上篇）：C盘清理.md" >}})），这次是下篇，做三件事：
- D 盘、E 盘大扫除
- 目录结构重新规划
- 最后把软件更新固化成维护技能

动机很实际。这台电脑装过又卸过大量软件，长期处于黑箱状态：电脑管家只能清理一部分，注册表残留、更新器、幽灵文件都在它视野之外；手动翻文件夹几乎不可能完成，目录又多又深，不知道哪些有用哪些是垃圾；命令行能解决，但自己敲不熟。AI 补齐了最后一环——**我判断，它执行**。

这次也彻底摆脱了第三方管家软件——卸掉它之后，由 Windows 自带的 Defender 接管实时防护，没有留空窗。

### 🤖 让AI跑，我来判断

这次清理最大的变化是协作方式：我不记命令，只做判断。循环是固定的——让 AI 扫描、AI 列出清单、我逐项决定删或留、AI 执行、AI 回读结果验证。整个过程里，我只需要回答一个问题：这个，要不要。

这个循环里用得相当多的操作，是 Ctrl+Shift+C。看到可疑的目录或文件，在资源管理器里选中、复制路径，直接发给 AI："扫一下这个目录"。它会把里面的结构、占用、更新时间、可能的身份全部查出来，我再决定怎么处理。这一轮清理里，这个动作重复了几十次——卸载残留、黑箱文件、占位目录，全靠它把"看得见但看不懂"的东西变成"看得懂再决定"。

所以这篇文章不列一堆命令让你背。你只需要会两件事：把路径发给 AI（Ctrl+Shift+C），以及回答"要不要"。剩下的交给 AI 跑——它比你更懂命令行，**你只要比它更懂自己**。

### 📦 卸载网盘演示

以卸载夸克网盘和阿里云盘为第一个例子，走一遍这个循环。

直接告诉 AI“帮我查询夸克网盘、阿里云盘的相关位置，并帮我卸载干净试试”，AI 先用官方卸载器静默卸载，顺利。然后继续让 AI 扫描残留，列出一份清单：Program Files 下的更新器目录、AppData 里的数据目录、ProgramData 里的阿里保护组件、两个后台服务、注册表里一串键。我逐项看——这些都是卸载程序没带走的，删。

普通权限删不动的部分（Program Files、HKLM、服务），让 AI 换管理员权限执行，一次成功。最后验证：安装目录、AppData、注册表、服务、自启动全部无残留。

收尾时发现"此电脑"里还挂着一个夸克网盘的图标，点不开。让 AI 查注册表，定位到 NameSpace 下的虚拟磁盘注册项——程序文件删了、注册项没删，留下尸体图标。删掉注册项、重启资源管理器，解决。同位置还有百度网盘的同款条目，还在用，保留。

一个流程演示下来，要点只有一个：写命令行、跑命令行都是 AI 的事，我只需要负责**判断**。

## 🕳️ 黑箱文件清理

清完网盘继续扫 D 盘，发现大量"黑箱文件"：同一软件的两个版本、卸载后的残留壳、弃用账号的数据、旧版安装包。它们的共同点是——平时没人知道它们存在，也不知道占了多少空间。老办法：看到不认识的大目录，Ctrl+Shift+C 发给 AI 核对。

### 📂 双份目录之谜

Program Files 和 Program Files (x86) 下同时存在 QQ 和腾讯会议。原因有两层：腾讯软件模拟系统目录结构、按位数分家；以及升级从不清理旧版本。具体格局：

- 新版 QQ（NT 架构，64 位）在 `Program Files\Tencent\QQNT`，卸载条目只登记这一份
- 旧版 QQ 9.x 在 (x86)，堆着 6 个版本的 Resource 目录（9.5.9 → 9.7.22）和 3 个安装包缓存
- 腾讯会议新版 3.44.1 和旧版 3.32.3 并存

旧版 QQ、旧版会议、OCR 空壳合计约 1GB，全部删掉。聊天记录在 `%APPDATA%\Tencent`，不受影响。

### 🏷️ 旧版与微信改名

微信也有一份"双份"：Weixin 是微信 4.0 之后的安装目录名（当前版本 4.1.12.55），WeChat 是旧版 3.x 的残留壳，里面只剩一个 0.1MB 的 WeChat.exe.zip（2025 年 5 月的旧主程序备份）。删掉。以后看到两个 Program Files 下同名软件并存，处理思路固定：对比版本号 → 看卸载条目 → 删旧留新。

### 🗃️ QQ 数据清理

`D:\QQdata` 有 40.38GB，四个数字文件夹是四个 QQ 号的数据。主力QQ号有 30GB（聊天记录备份 MsgBackup 13.6GB + 新版 QQ 数据 nt_qq 9.3GB + 聊天记录库 Msg3.0.db 5.6GB），另外三个账号 2024 年起就没登录过。新数据已迁到 `D:\03.Resources\Tencent`。旧目录里还有个 qqpcmgr_docpro——2023 年某工作时期腾讯电脑管家"文档保护"的备份，套餐产品文案都过期了。确认后一起删，释放约 23.7GB。

这次清下来发现，重复备份文件是黑箱文件的一大来源：QQ 的旧版本目录、MsgBackup 聊天记录备份、管家的文档备份、微信的旧主程序 zip——全是"备份/旧版"堆积。

### 🧩 必剪与直播姬

查必剪时发现它本体其实早就卸载了，只剩历史数据散在四处：`D:\AppData\BcutBilibili`（555.5MB 程序数据/缓存）、文档里的 Bcut Drafts（旧草稿）、AppData 里的 BCUT 配置和缓存（约 250MB）。合计约 800MB，一次清完。文档目录里还顺手清掉了 WeChat Files 空壳和 WXWork 旧数据（存储位置已改，旧目录无保留价值）。直播姬则是软件本体早被卸过、但目录和 AppData 残留还在，清掉后注册表里留了一条 InnoSetup ACL 保护的卸载项，删不掉也无害，容忍。

## 🔧 注册表检测并清理修复

目录重构的第一步是建立软件区（细节在下一节），战网先搬了进去。紧接着把 `D:\Programs` 里 4 个绿色软件也收编进 Portable——Python 的迁移把注册表问题牵了出来。

### 🔗 迁移引出断链

4 个软件合计约 25.8GB：CloudMusic 415MB、Python3.10.6 3.3GB、Python3.13 171MB、Ultimate Vocal Remover 21.9GB。同盘移动瞬间完成，但 Python 不能只挪文件——注册表 PythonCore InstallPath、用户 PATH、机器 PATH、开始菜单快捷方式都要同步改，漏一个 Python 就"找不到"。

迁移时挖出一个隐藏很久的问题：Python 3.13 的注册表、PATH、快捷方式全部指向 `D:\Programs\Python313`——这个目录根本不存在（实际目录叫 Python3.13，被改过名但绑定没跟着更新）。也就是说 3.13 一直是断链状态，平时敲 `python` 跑的是 anaconda。

### 🛠️ 断链修复

把 Python 3.13 的全部绑定（注册表 InstallPath、两处 PATH、快捷方式）修正为新位置，验证 py 启动器能同时识别 3.13 和 3.10，两个 python 直接运行正常。这次顺带确立了检查思路：绿色软件迁移后，注册表、PATH、快捷方式是三个必查的绑定点，任何一个指向失效路径都是断链。

### ✅ 影响面验证

改完担心影响自部署项目，专门扫了一遍：index-tts 用的是 uv 管理的 Python 3.11.13（独立安装）；GPT-SoVITS 用自带 runtime\python.exe（整合包）；全盘配置文件无一处写死 D:\Programs 路径，计划任务和服务没有 Python 引用。结论：三个 Python 体系是三条平行线，这次动的是第三条。唯一注意点是已打开的旧终端里 PATH 还是旧的，重开终端即恢复。

## 🗂️ 目录结构重新规划

清理告一段落，开始系统性地重新规划目录。骨架是之前就定的 PARA——Projects（进行中的项目）、Areas（长期维护的领域）、Resources（可复用的素材资源）、Archives（归档），规划文档（PARA-Migration-Plan.md）一直躺在 E 盘归档区，这次算是落地执行了一部分。

### 🗺️ PARA布局

四区分布在这两块盘上：D 盘的 02.Areas 装软件和知识库（Software、ObsidianVaults、Hugo 站点）、03.Resources 装素材和数据（SystemFolders、腾讯数据），E 盘的 02.Areas 放游戏库、04.Archives 放归档（照片、旧项目）。清理前各区职责模糊，软件、缓存、下载中转站混在一起；清理后各归其位——软件进 02.Areas，素材进 03.Resources，旧物进 04.Archives。

### 🗄️ 系统文件夹

6 个系统文件夹（桌面、下载、文档、图片、音乐、视频）统一收进 `D:\03.Resources\SystemFolders`。过程中遇到了三个问题，同样使用开头说到的方法依次验证并解决：

- 视频坏指向：注册表里系统"视频"指向 `G:\视频`，而 G 盘根本不存在（外接硬盘早拔了），潜伏了很久的坏指向，重指向 Videos 并修掉三处注册表引用。中间误删过正确的 FOLDERID_Videos 键，对照 FolderDescriptions 才发现键名本身才是 KnownFolder 的官方 GUID，纠正后正常
- System 属性之谜：5 个中文目录显示成英文内部名（Downloads、My Music），因为 desktop.ini 要生效、文件夹必须带 System 属性；用 `attrib +s` 补齐（Hidden 目录用 `attrib +s +h` 绕保护），显示名全部恢复中文
- 快速访问的误会：视频"在左侧看不到"其实是方向错了——快速访问默认只固定桌面/下载/文档/图片 4 个，音乐视频本来就不在里面；用 `InvokeVerb('pintohome')` 把视频固定进去

### 📁 软件区与路径归位

软件区定型为 `D:\02.Areas\Software`：Portable 收绿色软件（命名用 Portable 而非 GreenSoft，是绿色软件最通用的说法，战网、CloudMusic、Python×2、UVR 集中于此），MediaEdit 收编辑工具（剪映、OpenSource 里的 GIMP）。原则是工具与数据分离，软件区整体可备份可迁移。

分区规划好之后还有关键一步：把每个软件的默认存储路径指到对应分区，不然它们还是会偷偷写回 C 盘和根目录。这次统一设置了一批：

- 剪映：缓存、草稿、预设、封装、代理文件夹全部指到规划位置
- 下载类：QQ音乐、网易云、度盘、迅雷的默认下载目录和缓存
- 录制类：OBS、N卡录制的录像位置
- 达芬奇：缓存位置

原则是让"可再生数据"（下载、缓存）与"重要资产"（素材、项目）各归其位。路径稳定之后，下次清理时一眼就能看出哪里该清。

### 🎬 素材区

达芬奇的工作区也纳入规划。内部结构（01_Projects 项目库、02_Source_Media 通用素材库、04_Temporary_Project_Assets 项目专属素材——119.2GB，名字很误导，它不是缓存）是以前就规划好的，这次只做了一件事：换上级目录——从 E 盘根目录挪进 02.Areas 下的 MediaRepos\DaVinci，不让它再占着磁盘根目录，避免杂乱。软件本体和缓存放 D 盘，`E:\cache`（6.7GB 旧缓存）删掉。项目库断连重建手动完成，旧项目素材清空重来。

## ✂️ 剪映搬家与误删

应用数据区规划落地的第一个案例是剪映——程序本体住在 `AppData\Local\JianyingPro`（13.47GB），不想让它继续侵占 C 盘。

### 🔀 junction桥接

剪映搬到 `D:\02.Areas\Software\MediaEdit\JianyingPro`，原路径用一条 mklink 命令建 junction 桥接，把 `AppData\Local\JianyingPro` 重定向到新位置。junction 是文件系统层的重定向：任何程序访问原路径，内核自动转发到 D 盘。剪映的更新器、后台服务全都无感，以后更新直接写进 D 盘。唯一注意点：将来卸载剪映前要先删掉链接（用 rmdir，不能用 Remove-Item——它会顺着链接把目标一起删了）。

### ⚠️ 误删主程序

搬家后想对齐桌面快捷方式，读快捷方式目标发现指向 `Apps\JianyingPro.exe`，但这个文件全盘都找不到——复盘才发现：最初清理 AppData 时，把藏着主程序的 Apps 目录当成缓存整个删了，只留下 VEDetector 等零碎文件，当时误以为"程序本体还在"。也就是说剪映已经打不开了。这是这次清理中唯一的重大失误。

### 🔄 重装收尾

补救：重新下载官方安装器。重装时发现，剪映现在也可以手动设置安装目录了——这次直接装到 `D:\02.Areas\Software\MediaEdit\JianyingPro`，不需要再靠 junction 桥接。装完删掉 C 盘 junction、清掉全部残留，AppData 里再没有剪映的痕迹。

## 💾 E盘重构

E 盘是最后一块。清理前它同时承担着游戏库、达芬奇数据和一堆系统占位目录；重构后，E 盘根目录只剩 PARA 四区。

### 🎮 WeGame全家桶

`E:\WeGameApps` 134.3GB——天刀和 LOL 的 WeGame 版游戏库，两个游戏都不玩了，直接删。期间确认了 `D:\GameVideos`（deltaForceRecord + lolhighlight）的来源：WeGame/游戏内置的"游戏时刻"自动录制输出目录，游戏删了就不会再生成，空壳可清。WeGame 客户端也有两份：D 盘的在用（wegame.exe 当天还在更新），E 盘的是 2025 年 4 月的旧版，删 E 盘的。这轮实际释放约 225GB（含一次失败的移动操作在 E:\02.Areas\Games 下留下的 90GB 副本）。

### 🚚 Steam库搬家

Steam 的库文件夹机制有点反直觉：UI 里只能选盘符，选了 E 盘它就自动建固定名 SteamLibrary，文件夹名是死的。但路径其实可以改——libraryfolders.vdf 就是官方配置。这套方案是问 AI 问出来的：手动改 vdf 根本不知道从哪下手，让 AI 查了机制、给了完整步骤，照着做完、启动验证确实可行。步骤：完全退出 Steam → 备份 vdf → 移动文件（根目录带特殊 ACL，整体 move 被拒，改成先移内层 steamapps 再删空壳）→ 改 vdf 里库 1 的 path → 启动验证。8 个在册游戏全部正常识别，游戏库最终落在 `E:\02.Areas\Games\SteamLibrary`。顺带对照 appmanifest 清掉 26 个卸载残留的游戏文件夹——包括黑神话悟空，确认过它不是已安装状态。

### 👻 系统占位目录

E 盘根目录还躺着几个看着就不对的目录：ModifiableWindowsApps、WindowsApps、.GamingRoot、PSAutoRecover。老办法——Ctrl+Shift+C 复制路径，逐个发给 AI 扫：

- ModifiableWindowsApps：商店"可修改应用"占位，0MB
- WindowsApps：TrustedInstaller 锁定的空壳，takeown 夺权后删
- .GamingRoot：游戏盘隐藏标记文件，68B
- PSAutoRecover：PS 自动恢复目录，下次运行会重建

确认身份后全部清掉。03.Resources 和 04.Archives 也定了纯英文命名方案（Anime、OBSRec、VideoTemplates 这类），手动完成。

## ⬆️ 软件更新与skill练成

大扫除收尾，进入例行维护阶段。这次更新统一走 winget——Windows 自带的命令行包管理器，微软官方软件商店的终端形态，一条命令完成搜索、安装、升级、卸载。

### 📡 winget更新战报

体检结果：两块 Samsung 990 PRO 全部 Healthy，Defender 实时保护正常，RTX 3070 驱动是一个月内的版本。winget 列出 24 个可更新，分几轮批量跑，最终装好 13 个：VCRedist×2、Python 3.13.15、Python 3.10.11、VSTOR、微信、QQ、PotPlayer、网易云、腾讯会议、百度网盘、Apple 支持、Outlook（战网自己更新自己的）。放弃两个：Bonjour（新版 Apple 组件自带）和 WSL（大包下载失败）。Edge 走手动（winget 管不了系统级）。迅雷则是"脱管类"软件——winget 根本搜不到它，确认后台进程全退、无自启项，不用禁。

### 📋 决策规则与坑位

更新过程沉淀出一套判断规则：白名单（放心更）、黑名单（Anaconda 别动——IndexTTS 的 conda 环境）、手动（Edge、Adobe 系）、可卸（OneDrive、SteelSeries）、容忍（直播姬的 ACL 残留删不掉就无视）。坑位也记了一串：Outlook 是 MSIX 商店应用，静默安装容易卡住；Ollama 从 GitHub 下载国内慢，要后台跑；网易云升级会偷偷重加开机自启，装完必查启动项；百度网盘更新易超时，改用 PowerShell 包装后台跑再等待验证。

### 🎓 skill练成

维护流程跑顺之后，决定把这次的经验固化成可复用的东西。之前接触过 skill 的概念，但一直没细究；这次清理完成后，才认真搜索确认了它的具体含义——把一组规则和脚本打包、由触发词自动加载执行。于是把电脑维护流程作为第一次 skill 练成的尝试：主流程（体检 → 决策 → 更新 → 清理 → 验证）、决策规则表、坑位记录、清理分级，外加两个脚本（体检报告、白名单批量更新），打包成 windows-maintenance 技能。以后说一句"维护下电脑"就自动走全套。实测调用了一轮：百度网盘 8.7.2 → 8.7.9、TEMP 释放 1.17GB、迅雷确认干净、Anaconda 没被误更——决策规则全部按预期工作。

## 💡 维护方式的转变

### 👁️ 黑箱与白箱

这次最大的收获不是空间，是维护方式本身变了。以前用电脑管家，一键清理很省事，但它是黑箱：清了什么、为什么清、有没有误删，都看不到，而且它管不到注册表修复、更新器、服务这类"管家视野之外"的东西。换成 AI 加命令行之后，每条命令、每个删掉的文件、每处注册表修改都看得见、可回滚、可验证——电脑从黑箱变成了白箱。AI 的价值不是替我做判断，而是把"想做的"翻译成"能执行的"，再把"执行结果"翻译回"看得懂的"。

### 🗑️ 残留文化

这轮清下来的另一个感受：国产软件的卸载普遍不彻底。升级从不清理旧版本（QQ 堆了 6 个版本的资源目录）、网盘在"此电脑"里留尸体图标、管家类组件卸完还残留保护组件和文档备份。"卸载干净"从来不是点一下卸载按钮，而是一套固定的排查流程：安装目录、AppData、注册表（含 NameSpace 这类冷门位置）、服务、自启、计划任务。电脑越用越乱，不是因为软件多，而是每个软件都留下一层壳。

### ⚖️ 判断优先于执行

整个维护过程最有价值的不是命令，是判断：哪些能删（弃用账号、缓存、残留）、哪些别动（Anaconda、主力号数据、来历不明的缓存）、哪些容忍（ACL 残留、脱管软件）。命令是死的，判断是活的。这条也直接决定了维护技能的设计——决策规则表比执行脚本重要得多。

### 📚 沉淀为资产

这次清理还有一个背景。动手前几天，意识到 AI 可以直接读取本地文件，于是提炼了几个不同用途的规则文档（AI 助手提示词），统一放在 Assitant-Prompt 文件夹里，用主助手调用——既能保持对话背景的一致性，又能按需切换规则、互不冲突。这轮清理就是在这个机制下完成的。

确认了 skill 的具体含义之后再回头看，才发现自己原本在做的事情已经很接近 skill 的使用了，只是没有自动加载而已。于是决定先把电脑维护流程提炼成 skill 试试水：如果验证可行，后续再把其他规则也逐步转成 skill，提升便利。这次实践下来才真正体会到差别：规则文档是菜谱，得自己翻出来递给厨师；skill 是装进厨房的语音厨师，说"做道菜"它自己就开工了。

所有经验最后都沉淀成了可复用资产：维护技能、九条坑位记录，以及这篇记录本身。累计找回的四百多GB空间只是表面收益，真正留下的是这套以后每次维护都能用的方法论。

备注：文中"它比你更懂命令行"是从普通用户视角说的。但即便对高级程序员，反复敲命令行也是耗时耗力的事；不过这是我作为普通用户的推测——也许程序员有更习惯的维护方式也说不定，这个就超出本次认知范围了。
