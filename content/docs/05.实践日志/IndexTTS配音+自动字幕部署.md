# 🎙️ IndexTTS 配音+自动字幕部署
---

## 原因说明

### 💭 起因：效率瓶颈在哪

**生成环节**：
视频配音长期使用 GPT-SoVITS
- 生成需要反复调参试音
- 一段旁白往往要尝试多次才能得到满意的结果，效率不稳定。

**修剪环节**：
问题更突出：
- 剪映识别后导入达芬奇，还要逐句校对气口和断句
- 一条二十分钟的视频光校对字幕就要两个小时。

这两个环节占据了大量时间，且都是重复劳动。

于是决定搭建一条本地流水线，期望：
**写稿之后，配音和字幕尽量自动化，人工只做最终修剪**。

## 一、AI辅助：DeepSeek API 与 Chatbox

整个部署过程并不是独立完成的，而是在 AI 的协助下推进的。
- 对话模型来源：**DeepSeek API**
- 前端窗口使用：**Chatbox**。

### 🤖 专属助手与工作模式

配置上做了两件事：

1. **专属助手**：用 AI 优化提示词，针对本项目设置了一个专属助手
	- 把项目背景、硬件环境、目标写进系统提示词，
	- 后续对话不用重复交代。
2. **工作模式**：启用了联网搜索和代码执行。
	- 联网搜索用于查资料、核实官方文档；
	- 代码执行是关键——AI 不只是给建议，它能直接在本地运行命令行、读取文件、修改脚本。

### ⌨️ 关于命令行

很多自部署的项目（比如 Hugo 建站，或者其他 GitHub 项目）是没有图形操作界面的
- 只能通过命令行来设置。
- 这跟我们平时用惯的图形界面——“鼠标点击”、“拖拽”不太一样。

> 注：这一点需要先接受——**命令行**是必经之路。
不会的、不懂的，问 AI 即可，算是AI时代的红利

目前AI的普及把技术门槛降到了很低。
本人在英语水平和 Python 语法上的了解都很有限，按传统方式，这类部署需要读英文文档、理解依赖关系、会写脚本；
而这个流程把"需要做的事情"从"自己写代码"降低到了"把遇到的问题发给 AI"
——AI 能本地读取文件，定位问题，直接修改完善，再交回验证。

后续所有环节，包括部署排错、脚本编写、规则落地，都是在这个工作方式下完成的。

## 二、工具选择：选IndexTTS 2.5的理由

最终选定 B 站开源的 IndexTTS 2.5，仓库地址 `https://github.com/index-tts/index-tts`（2.5 版本 2026-08-10 发布）。选它的理由如下：

### 零样本克隆：
提供一段 5~15 秒的参考音频即可克隆音色，不需要训练过程，解决了 GPT-SoVITS 调参炼丹的问题。
### 硬件要求低
0.8B 参数，BF16 半精度推理，8G 显存的 RTX 3070 即可运行（我的硬件刚好达标）。
### 其他优点
- **多语言支持**：
	- 覆盖中英日西阿，日常中文为主
	- 偶尔出现的英文和游戏台词也能处理。
- **可控性强**：
	- 支持情感提示、语速调节（0.5~2.0 倍）、拼音发音控制
	- 游戏专有名词可以指定读法。

## 三、部署准备：前置环境

部署前先确认前置环境，分三部分：Git、Python（含环境管理工具 uv）、硬件。

### 🐙 Git

git 是克隆仓库、管理代码版本的工具，本项目依赖它从 GitHub 拉取源码。本机已装 git 2.55.0；若未安装，官网 `https://git-scm.com/` 下载 Windows 版安装包，默认选项安装，装完命令行 `git --version` 验证。

另外需要 git-lfs（拉取仓库大文件用），从 `https://git-lfs.com/` 下载安装，装完运行一次 `git lfs install`。

### 🐍 Python 与 uv

本机已有系统级 Python 3.10.6，但本项目并不依赖它——项目锁定 Python 3.11.13，由 uv 自动管理，不会影响系统 Python。

uv 是官方推荐的环境管理工具，安装命令：

```
pip install -U uv
```

验证：`uv --version`。

uv 会在项目文件夹内自动创建独立的虚拟环境 `.venv`，并自动下载项目所需的 Python 版本装进去，不依赖系统 Python，也不影响其他项目。

> 理论上Docker也可以用来封装，但相对繁琐
uv 的虚拟环境已经能满足隔离需求，更轻量，且官方主推的就是 uv 方案。

### 🖥️ 硬件

显卡内存：我的设备是是 RTX 3070 8G，满足模型的最低要求（0.8B 参数，BF16 半精度推理，8G 显存可运行）。
显卡驱动：需要较新版本（支持 CUDA 12.8+，约 572 系及以上），用之前先更新即可
```
nvidia-smi
```

可查看当前驱动版本。

磁盘空间：至少 30GB（模型加环境约 15~25GB）。

## 四、部署过程：在本地端使用

### 📥 Git克隆仓库

git clone 会把仓库生成在当前目录下，所以先想好存放位置。做法：
- 在文件资源管理器里建好目标文件夹（例如 `E:\02.Areas\AI-Tools`）
- 双击进去，在地址栏输入 `cmd` 回车，打开的终端直接就位于这个目录，然后执行：

```
git clone https://github.com/index-tts/index-tts.git
cd index-tts
git lfs pull
```

> ⚠️ 若直连失败，处理办法见下文"网络问题的处理"。

### 🧩 安装依赖

在仓库目录内执行（必须在有 `pyproject.toml` 的目录下运行）：

```
uv sync --extra webui --default-index "https://mirrors.aliyun.com/pypi/simple"
```

这一步会自动创建 `.venv` 并安装依赖，耗时约 20~40 分钟。两个注意点：

- 不要用 `--all-extras`，它会安装 DeepSpeed，在 Windows 上极难安装且容易卡死。
- 若阿里云镜像报错，换清华镜像：`https://mirrors.tuna.tsinghua.edu.cn/pypi/web/simple`。

### ⬇️ 下载模型

模型走 ModelScope 下载（国内快，相当于镜像思路），约 0.8B 参数，下载到仓库内 `checkpoints/` 目录：

```
uv tool run modelscope download --model IndexTeam/IndexTTS-2.5 --local_dir ./checkpoints
```

### 🌐 网络问题的处理

本项目涉及多处网络下载：克隆 GitHub 仓库、安装 Python 依赖、下载模型。直连都可能失败或极慢，处理办法有两个：

1. **使用镜像**：克隆仓库用 GitHub 镜像（如 `gh-proxy.com`）；依赖走国内 PyPI 镜像；模型走 ModelScope 或 `hf-mirror`。
2. **科学上网**：详细方法不可解释，需要自行研究。

对应到各步骤：克隆失败（curl 28 超时）时，改用

```
git clone https://gh-proxy.com/https://github.com/index-tts/index-tts.git
```

克隆成功后把远程源改回官方地址，方便以后拉取更新：

```
git remote set-url origin https://github.com/index-tts/index-tts.git
```

依赖和模型同理：依赖换 PyPI 镜像，模型走 ModelScope（国内，一般不会失败）。

### 🚀 启动 WebUI

启动命令注意必须带 `--version 2.5`，默认是 2.0：

```
uv run webui.py --version 2.5 --model_dir ./checkpoints --fp16
```

浏览器打开 `http://127.0.0.1:7860`。首次启动会自动下载少量辅助小模型。
可用 `uv run tools/gpu_check.py` 确认 GPU 加速生效。

首次测试：上传一段参考音频（建议 5~15 秒清晰人声），输入测试文本，点生成。

### 🗃️ 启动器的封装：.bat 的作用

部署完成后，由于每次启动都要敲一长串命令（在项目根目录中打开命令行运行）
```
uv run webui.py --version 2.5 --model_dir ./checkpoints --fp16
```

故把命令封装成一个启动文件，也即后缀为 `.bat`的 文件，封装好后，双击即启动。

>**`.bat` 说明：就是把几条命令行打包在一起运行的文件**，

作用是简化敲命令的过程。背后其实只干了三件事：
- 找到环境（定位 `.venv` 里的 python）
- 进入项目目录（`cd /d` 到仓库位置）
- 把命令行参数固化（启动命令写死在 bat 里）

手动敲什么命令，bat 里就写什么。

## 五、显存问题的处理
### 进程频繁崩溃

部署完成后，实际使用中遇到的主要问题是显存崩溃。
- 8G 显存运行该模型时，生成会随机报错，日志中常见 `CUDA context corrupted`
- 而且经常在生成的第 0 步就崩溃。

排查并不是"发现问题、直接解决"这么简单。
- 整个过程是把报错日志、运行现象、显卡状态持续发给 AI
- 由 AI 判断排查方向、给出验证步骤，逐轮执行、逐轮排除
- 多轮往返之后才把问题收窄到硬件层面

——不是显存逐步占满导致的，而是硬件状态本身处于临界(大概率是老化、损耗）
>打游戏时也会出现瞬时显存爆掉的情况，属于硬件层面的不稳定，软件无法根治。

### 流程优化对治
处理方式是让流程替硬件兜底，而不是反复查错：

1. **生成策略调整**：
	- 参考音频控制在 5 秒内，单次生成文本控制在 300~400 字
	- 开启 fp16 降低显存占用。（具体让AI写入的，细节我也没记）
2. **启动器自愈**：
	- 把启动器升级为自动重启模式，生成失败时程序自动重启
	- 重启后自动恢复上次的参数（文本、参考音频、情感设置）
	- 服务就绪后自动打开浏览器页面，可以直接继续生成。

> 💡 调整之后，日常分段生成的失败带来的影响降低到可接受范围，不至于中断工作流、影响心情。

## 六、语音转字幕的实现

### 🤔 为什么不能估算时间戳

最初考虑用"字数 × 语速"估算字幕时间戳，实测不可行。原因是 TTS 在标点处的停顿是模型即兴产生的，语速也不是均匀的，强调处慢、带过处快。一段五百字的文本，每字误差二十毫秒，累计就会漂移数秒。

### 👂 用 Whisper 转写获取时间戳

正确的做法是让语音识别模型 Whisper 直接"听"出时间戳。由于音频本来就是照着文稿生成的，转写文本与原文稿高度一致，因此可以拿转写结果作为字幕文本。

这里有一个关键设计：**不能直接使用 Whisper 的输出**，因为 Whisper 有自己的断句逻辑，行与行之间会与文稿不一致。实际做法是：

1. 将分段音频合并为完整音频。
2. 用 Whisper 转写，得到带时间戳的转写文本。
3. 将转写文本与原文稿做模糊匹配，逐句定位，把 Whisper 的时间戳映射到文稿的每一行上。

这一环节的脚本编写与调试同样是在 AI 协助下完成的：先把需求描述给 AI，由 AI 写脚本，再用真实音频反复测试，把报错和异常结果发回给 AI 校对、修改，直到对齐逻辑稳定。

> 💡 匹配失败的行，恰好就是 TTS 读法与文稿不一致的地方（例如数字、英文的读法差异），相当于附带了一个质检功能。

实测结果：242 行文稿匹配成功 238 行，**匹配率 98.3%**。未匹配的 4 行集中在三类情况：

- 阿拉伯数字：文稿中的 `10血1攻`，TTS 读作"十血一攻"，转写为中文数字，与原文对不上。
- 英文：`Build`、`BOSS` 等，TTS 的读法不可控。
- 括号备注：`（仁王2）` 这类括号内容，TTS 朗读节奏与文稿字面不一致。

## 七、文稿规则的建立

分析未匹配的原因后发现，问题不在脚本，而在于文稿本身没有为"TTS 朗读 → 转写对齐"这条链路做过优化。于是制定了三层文稿规则。

### ✂️ 断句规则

- 每行不超过 25 字，这是字幕单行上限，也是时间戳精度的分界线。
- 一行一意，宁可多拆一行。
- 行边界必须是朗读时会自然停顿的位置。
- 切分优先级：句末（句号、问号、感叹号）优先，其次是停顿（逗号、顿号），最后才是硬切。

### ✒️ 标点规则

- 句号、问号、感叹号正常使用。
- 逗号少用，能断行就断行。
- 分号拆成两句。
- 省略号、破折号避免使用，因为 TTS 读法不可控。

### 🔤 内容规则

- 括号一律视为备注：不朗读、不进字幕，预处理时连同内容整体删除。
- 英文转中文或中文谐音：`BOSS` 写作"首领/波死"，`XX` 写作"叉叉"，以此类推。
- 阿拉伯数字转中文数字：`难9深30` 写作"难九深三十"。

### 🧠 文稿助手：规则的第二种落地

规则定稿后，落地为两个工具。一是预处理脚本：去除 markdown 符号、删除括号备注、按规则断句、检测残留的英文和数字并给出提醒。二是**"文稿助手"提示词**：把上述规则整理成一份系统提示词，在新对话里直接设置即可使用，让 AI 按同样的规则改写已有文稿（删备注、英文数字转中文、重新断行），并在输出末尾列出所有删改的位置供核对。

> 💡 两者分工：脚本负责机械处理（删备注、断句、检测），AI 按提示词负责语义处理（英文、数字转中文）。推荐流程是脚本先跑一遍，把提醒里残留的英文数字交给 AI 按提示词转中文，得到干净的"朗读版"文稿。

## 八、最终流程

流程并非一次设计成型。先用一篇旧文稿配合新工具链完整测试了一轮：从文稿预处理、分段生成音频，到合并转写、对齐出 SRT，确认每个环节衔接无误、结果可用后，才沉淀为固定流程：

1. Obsidian 写稿，备注放入括号。
2. 文稿拖入预处理脚本，自动删备注、断句、检测残留。
3. IndexTTS 分段生成音频，启动器兜底自动重启。
4. 音频文件夹拖入字幕脚本，合并音频、Whisper 转写、对齐文稿、输出完整 SRT。
5. 达芬奇成片，人工修剪气口、微调字幕。

> 📝 从文稿到可剪辑素材，字幕环节已接近全自动，人工剩余的工作是修剪气口和打磨节奏。

## 九、关于整合包：打包的含义

项目跑顺之后，曾经考虑过把整个 `index-tts` 文件夹打包发给别人使用——因为 `.venv` 就在项目文件夹内，环境是自带的，理论上解压即用。

讨论后确认了这个思路的本质：**整合包 = 环境隔离（.venv）+ 一键启动（.bat）**。环境隔离解决的是"换机器不用装环境、依赖不污染系统"，一键启动解决的是"使用者不用懂命令行"。两者合起来就是"解压即用"。以前用过的其他整合包里都有 `.bat` 文件，原因就在这里——它是给不懂命令行的人准备的简化入口。

同时确认了原样打包不可行，有四个坑要处理：

1. **绝对路径**：bat 里的路径是写死的，别人电脑上不存在，需要改成便携写法（用 bat 自身所在目录）。
2. **uv 依赖**：接收方没有装 uv，需要让 bat 优先使用包内的 python 环境。
3. **隐私清理**：个人参数、测试音频、缓存目录都要删除后才能发人。
4. **体积分发**：环境加模型约 9~10GB，只能走网盘分享。

最终决定暂时不打包，只是确认思路。因为这套工具现阶段是自用的，打包给别人属于"面向别人的工具"，要做加法（容错、检查、说明文档），而当前阶段应该继续做减法。

## 十、最后总结

这次改造中，收获最大的不是流水线本身，而是背后的工作方式。

### 🤖 AI 协助

以前遇到技术问题，需要自己查文档、看代码、试错；现在只需要把问题描述清楚发给 AI，AI 可以读取本地文件、执行命令、修改脚本，再交回验证。这等于把技术门槛从"会写代码"降低到了"会描述问题"，英语水平和 Python 语法不再是硬性障碍。整个项目从部署到脚本编写，都是在这个模式下完成的。

### 🗂️ AI 的本地文件能力

AI 的能力还延伸到了项目之外。尝试过让 AI 分析 C 盘和 D 盘的目录结构与文件占用情况，据此做了一次存储空间优化，清理了很多以前不知道是什么、也不敢删的文件。

### 📚 几点技术经验

一是**命令行的使用**。自部署项目大多没有图形界面，命令行是必经之路；不熟悉不是障碍，问 AI 即可，但需要接受并习惯这种方式。

二是 **`.bat` 的作用**。把多条命令行打包成双击运行的文件，简化重复操作——详见部署一节。

三是**封装的含义**。把工具链里固定的命令、路径、参数固化下来，让使用门槛降到最低——详见整合包一节。

四是**规则的收益大于脚本**。匹配率从 95% 提升到 98% 以上，主要贡献不是脚本优化，而是文稿写法的约定。脚本只是规则的执行者。

五是**面向自己用的工具做减法**。路径固定、环境现成，容错代码能省则省，维护成本也是成本。

六是**把硬件的不稳定转化为流程的一部分**。显存崩溃无法根治，就通过重试和自动恢复参数让它不再打断工作节奏。
